# AGENTS.md — Great House Social Overhaul

## Назначение
GHSO — крупный мод для The Elder Scrolls III: Morrowind на классическом движке с MWSE-Lua. Цель — динамическая социальная система: богатство, репутация, влияние, формальное положение, титулы, привилегии, собственность, персонал и политика. Охват — весь мир, все расы, регионы и основные организации. Мод расширяет оригинальный лор без противоречий.

## Обязательные правила для Codex
1. **Не выдумывай MWSE API.** Перед использованием функции, события, типа, поля или метода проверь точное имя и сигнатуру в документации целевой версии MWSE либо в проверенном исходном коде/примере.
2. Отделяй подтверждённые возможности от гипотез. Неизвестное сначала проверяй минимальным экспериментом.
3. `GHSO.*` — внутренний API проекта, а не API MWSE, если это отдельно не подтверждено.
4. Не сохраняй игровые объекты напрямую. Сохраняй устойчивые ID и простые сериализуемые значения.
5. Любое изменение постоянных данных сопровождай обновлением версии схемы и миграцией.
6. Не сканируй весь мир каждый кадр. Используй события, кэширование и ограниченные проверки.
7. Не меняй ванильные записи без необходимости. Предпочитай изолированные интеграции и отдельные compatibility-плагины.
8. Не выдумывай лор, титулы, обычаи, полномочия организаций и географию.
9. Не выдавай заглушки за готовую механику и не заявляй о тестах, которые не запускались.
10. Не переписывай несвязанные модули и не меняй публичные контракты без необходимости.

## Технологические границы
- Игра: Morrowind, классический движок.
- Скрипты: MWSE-Lua.
- ESP/ESM: NPC, диалоги, предметы, ячейки, двери, размещённые объекты и другие игровые записи.
- MCM: интерфейс настроек при наличии в целевой конфигурации.
- `tes3conv`: кандидат на ESP/ESM ↔ JSON pipeline, но не замена Construction Set.
- Git: контроль версий.

Не предполагай, что любой контент можно создать только Lua-кодом. Не добавляй ESP-записи там, где достаточно Lua.

## Проверка API
Перед использованием MWSE API:
1. Найди API в документации целевой версии.
2. Проверь точное имя, регистр, сигнатуру, аргументы, возвращаемые значения и доступность.
3. Проверь время жизни объектов и допустимость вызова из выбранного события.
4. При неясности создай минимальный тест.
5. Для важных решений зафиксируй источник в `docs/API_NOTES.md`.

Не делай вывод о наличии функции по похожему имени или примеру для другой версии.

## Архитектурные правила
- Слои: Core, Domain, Systems, Integration, UI, Content.
- Доменная логика не должна зависеть от конкретных NPC, ячеек и ESP ID.
- Интеграционные адаптеры переводят события игры в вызовы доменных сервисов.
- Разделяй богатство, репутацию, влияние, формальный статус, титулы, привилегии и происхождение.
- Членство во фракции, ранг, общественная репутация и титул — разные понятия.
- Для каждого параметра определи источник истины: ванильные данные, состояние GHSO или вычисляемое значение.
- Не дублируй ванильные данные без причины; кэш должен иметь стратегию инвалидирования.

## Сохранения и миграции
- Все постоянные данные GHSO имеют документированный корневой формат и `schemaVersion`.
- Миграции последовательны (`v1 -> v2 -> v3`) и безопасно обрабатывают отсутствующие поля.
- Неизвестную более новую версию не перезаписывай молча.
- Временные кэши и ссылки на игровые объекты не считаются постоянными данными.
- Отключение необязательной интеграции не должно удалять профиль игрока.
- Проверь сериализацию, загрузку и миграцию в игре.

## События и производительность
- Предпочитай события изменения состояния полным периодическим обходам.
- Не выполняй тяжёлую работу в часто вызываемых событиях.
- Защищайся от повторной обработки одного события и циклов.
- Для периодических процессов документируй интервал, объём работы и возможность диагностики.
- Проверяй существование игровых ссылок перед использованием.

## NPC, диалоги и контент
- Lua не означает автоматическую поддержку всех ванильных диалогов.
- Для диалоговых изменений нужны проверенные точки интеграции и, возможно, ESP INFO-записи.
- Веди реестр поддерживаемых NPC и диалоговых ID.
- Учитывай порядок загрузки и конфликты с другими модами.
- Реакции должны учитывать контекст организации, региона, культуры и личных отношений.

## ESP/ESM и tes3conv
- Сначала проверь поддержку нужного типа записи и кодировки.
- Успешная конвертация не доказывает корректность плагина.
- Проверяй уникальность ID, ссылки, master-файлы, зависимости и load order.
- Сохраняй исходный плагин и анализируй diff.
- Диалоги, NPC, ячейки и размещённые объекты проверяй в игре.
- Интерьеры и пространственный контент визуально проверяй в Construction Set и/или игре.

## Лор
- Расширяй канон, не создавая альтернативную вселенную.
- Не делай одну социальную модель универсальной для всех культур.
- Не превращай расовую принадлежность в бездумный глобальный штраф.
- Не меняй ключевые события оригинала без отдельного обоснования.
- Новые механики должны иметь правдоподобное внутриигровое объяснение.

## Код
- Используй только синтаксис Lua, поддерживаемый целевой сборкой MWSE.
- Делай модули небольшими и с одной ответственностью.
- Не подавляй ошибки молча; логируй полезный контекст без спама.
- Избегай ненужных глобальных переменных.
- Не помещай всю логику в callback события.
- Комментарии объясняют причины и ограничения, а не очевидные строки кода.

## Тестирование
Перед каждой итерацией тестирования собери полный `release/GHSO-test.zip` из текущих файлов командой `python tools/build/package_test.py`. Запускай проверки после успешной сборки. В игровом прогоне используй содержимое свежего ZIP.

Разделяй:
1. статическую проверку;
2. изолированные тесты чистой логики;
3. тесты в игре;
4. проверки совместимости.

Smoke-тесты ядра: загрузка мода без Lua-ошибок; создание/сохранение/загрузка профиля; миграция старой схемы; работа Core без необязательных ESP; безопасная обработка отсутствующей интеграции.

В отчёте всегда указывай, что проверено автоматически, что проверено в игре и что осталось непроверенным.

## Рабочий процесс
Перед задачей:
1. Прочитай `AGENTS.md`, `ARCHITECTURE.md`, `TECHNICAL_DECISIONS.md`.
2. Осмотри репозиторий и текущие соглашения.
3. Определи затронутые модули и контракты.
4. Сформулируй краткий план.
5. Проверь неизвестные MWSE API до написания кода.

После задачи:
1. Запусти доступные проверки.
2. Проверь diff.
3. Обнови документацию при изменении контракта или решения.
4. Перечисли файлы, поведение, тесты и риски.

Задача готова, когда реализация соответствует требованию, ошибки и отсутствующие данные обработаны, тесты добавлены либо описан ручной сценарий, документация актуальна, а непроверенные моменты явно названы.

## Запреты на необоснованные обещания
Не обещай автоматическую реакцию каждого NPC, универсальную замену всех ванильных диалогов, полностью автоматическую генерацию качественных интерьеров, отсутствие конфликтов со всеми модами или корректность ESP без проверки в игре. Проектируй постепенное расширение покрытия мира.
