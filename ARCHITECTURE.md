# ARCHITECTURE.md — Great House Social Overhaul

**Статус:** начальная архитектура; уточняется после Technical Spike.  
**Платформа:** The Elder Scrolls III: Morrowind, классический движок + MWSE-Lua.

## 1. Видение
GHSO добавляет динамическую социальную модель, связывающую богатство, репутацию, влияние, титулы, привилегии, собственность и политику с реакциями игрового мира. Целевой охват — весь мир, все расы, регионы и основные организации. Мод расширяет оригинальный лор без противоречий.

## 2. Принципы
1. Lua/MWSE — правила, расчёты, состояние и оркестрация.
2. ESP/ESM — игровые записи и контентные точки интеграции.
3. Данные контента отделены от исполняемой логики.
4. Ванильные системы используются как источники данных, когда это семантически корректно.
5. Социальные характеристики независимы.
6. Интеграции модульны и отключаемы.
7. Сохранения версионируются и мигрируют.
8. Система событийная, без постоянного полного сканирования мира.

## 3. Компоненты

### GHSO Core (обязательный, Lua)
Загрузка модулей, конфигурация, логирование, постоянные данные, миграции, общие утилиты и реестр сервисов. Не содержит логику конкретного NPC, Дома или поместья.

### GHSO Base (ESP — только если нужен)
Общие игровые записи, базовые диалоговые точки, общие предметы и маркеры. Не создавай плагин, пока нет реальной потребности в новых записях.

### GHSO World (ESP + Lua)
Интеграции с Великими Домами, Имперскими организациями, Гильдиями, Храмом, Мораг Тонг, поселениями, регионами и выбранными NPC.

### GHSO Estates (ESP + Lua)
Недвижимость, доступ к помещениям, покупка, интерьеры, размещённые объекты, точки обслуживания, управляющие и персонал.

### GHSO Integrations (необязательные)
Compatibility-модули для сторонних модов. Они не должны быть зависимостями Core.

Физическое число ESP-плагинов определить после технического эксперимента: не дробить контент ради самой модульности.

## 5. Направление зависимостей

```text
Morrowind / MWSE
       |
MWSE-facing adapters
       |
   GHSO Core
       |
 Domain services
   /    |     \
Economy Property Politics
   \    |     /
Integration adapters
       |
 ESP / game content
```

Игровые адаптеры вызывают доменные сервисы. Доменная логика не зависит от конкретных ESP ID или игровых объектов. Доступ к движку изолирован в адаптерах.

## 6. Социальный профиль

Концептуальная модель:

```lua
{
    wealth = {
        liquid = 0,
        assets = 0,
        debts = 0,
    },
    reputation = {
        general = 0,
        regional = {},
        cultural = {},
    },
    influence = {},
    standing = {},
    titles = {},
    privileges = {},
    origin = {
        race = nil,
        culture = nil,
        background = nil,
    },
}
```

Это проектная модель, не API MWSE и не окончательная схема сохранения.

- **Wealth:** деньги, активы и обязательства.
- **Reputation:** общественная оценка.
- **Influence:** способность воздействовать на конкретную организацию.
- **Standing:** формальное положение в определённом социальном контексте.
- **Title:** признанное звание с источником и условиями.
- **Privilege:** конкретное право или доступ.
- **Origin:** контекст происхождения, который может учитываться отдельными обществами.

Не объединяй всё в `socialLevel`. Производные категории можно вычислять из исходных характеристик; они не должны становиться вторым источником истины.

## 7. Титулы и привилегии
Титул — запись с ID, условиями получения, источником признания, историей и последствиями. Привилегия описывает конкретное действие: доступ к помещению, возможность нанять персонал, особое обслуживание или участие в событии.

Пример определения данных (не MWSE API):

```lua
{
    id = "example_noble_title",
    grantingOrganization = "example_house",
    requirements = {
        minReputation = 50,
        minInfluence = 25,
    },
    grants = {
        "example_estate_access",
        "example_formal_address",
    },
}
```

Проверка привилегий проходит через единый сервис, чтобы не дублировать условия по разным модулям.

## 8. Организации и ванильные фракции
Для каждой организации опиши:
- внутренний стабильный `organizationId`;
- ванильный faction ID, если применимо;
- тип и социальный/географический контекст;
- используемые ванильные данные;
- собственные параметры GHSO;
- точки интеграции и необязательные зависимости.

Ванильные ранги и репутация фракций могут быть источником данных, но не описывают всю социальную систему. Не у каждой организации есть подходящая ванильная фракция.

## 9. NPC и диалоги
Интеграции должны быть декларативными, насколько это возможно, и перечислять NPC ID, контексты, условия и реакции. Это формат конфигурации GHSO, не встроенная функция MWSE.

Уровни:
1. **Системный:** disposition, доступность взаимодействий и другие механики — только через проверенные API.
2. **Контентный:** реплики, обращения, приглашения и отказы — через диалоговые записи ESP и Lua.
3. **Сценарный:** уникальные сцены, квесты и политические последствия — ESP + Lua.

Не обещай универсальную реакцию всех NPC. Сначала создай реестр реально поддерживаемых NPC и диалоговых точек. Учитывай конфликты с другими модами.

## 10. Экономика
Учитывай деньги, стоимость имущества, регулярные доходы, содержание, зарплаты, долги и обязательства. Каждая операция должна иметь источник, сумму, игровое время, категорию и метаданные. Предусмотри защиту от повторного начисления после загрузки сохранения или повторной обработки события: transaction ID либо эквивалентный механизм идемпотентности.

## 11. Недвижимость и поместья
Запись недвижимости содержит `propertyId`, владельца, тип, регион, цену, расходы, улучшения, связанные cell/interior IDs, услуги и состояние владения. Lua управляет правилами и состоянием; ESP предоставляет новые ячейки, двери, маркеры и размещённые объекты, если они нужны. Интерьеры требуют визуальной проверки в Construction Set и игре.

## 12. Персонал
Разделяй игрового NPC и контрактные данные GHSO. Для назначения храни роль, место работы, жалованье, доступность и состояние найма. Отсутствующий или удалённый другим модом NPC не должен ломать сохранение.

## 13. Политика
Политическая система учитывает организации, интересы, влияние, отношения, события, последствия и историю решений. Не создавай единую глобальную шкалу власти: влияние в одном Доме не означает автоматическую власть в другом.

## 14. Данные и валидация
Титулы, привилегии, организации, регионы и недвижимость описывай данными, если это упрощает расширение. Валидатор проверяет уникальность ID, обязательные поля, ссылки, числовые диапазоны и зависимости.

## 15. Сохранения
Предлагаемый корневой формат:

```lua
{
    schemaVersion = 5,
    player = { influenceAwards = {}, claimedPrivileges = {}, regionalReputationAwards = {} },
    economy = {},
    property = {},
    personnel = {},
    politics = {},
    history = {},
}
```

Первый срез Core хранит корень в `tes3.player.data.GHSO` и
инициализирует его после загрузки игры. Реализованный формат версии 5
описан в [DATA_SCHEMA.md](docs/DATA_SCHEMA.md). Проверка сериализации
в игре описана в [TEST_PLAN.md](docs/TEST_PLAN.md).

## 16. Внутренние API-контракты
Следующие имена — только проектные предложения, не API MWSE:

```lua
GHSO.social.getProfile()
GHSO.social.getWealth()
GHSO.social.getReputation(contextId)
GHSO.social.getInfluence(organizationId)

GHSO.titles.has(titleId)
GHSO.titles.grant(titleId, source)
GHSO.titles.revoke(titleId, reason)

GHSO.privileges.has(privilegeId, context)
GHSO.privileges.grant(privilegeId, source)
GHSO.privileges.revoke(privilegeId, reason)

GHSO.property.get(propertyId)
GHSO.property.purchase(propertyId)

GHSO.economy.addIncome(sourceId, amount, metadata)
GHSO.economy.addExpense(sourceId, amount, metadata)
```

Для каждого метода определить типы аргументов, возвращаемые значения, ошибки, побочные эффекты, повторные вызовы и влияние на сохранения.

## 17. ESP pipeline
`tes3conv` оценивается как инструмент ESP/ESM ↔ JSON:
1. получить исходный плагин;
2. конвертировать в JSON;
3. проверить структуру и кодировку;
4. внести ограниченные изменения;
5. собрать плагин;
6. проверить diff, ссылки и зависимости;
7. проверить в Construction Set/игре.

Конвертер не заменяет визуальное редактирование и тестирование.

## 18. Логирование и производительность
Логируй загрузку Core, активные интеграции, версию схемы, миграции и важные ошибки. Не логируй большие структуры на каждом событии. Не обходи всех NPC каждый кадр; используй события, ленивые вычисления и кэш с инвалидированием. Производительность проверяй в игре.

## 19. Совместимость
Core работает без необязательных интеграций. Compatibility-модули проверяют наличие зависимости. Документируй load order. Не редактируй записи стороннего мода без причины и отдельного compatibility-плагина. Веди список затронутых ID и известных конфликтов.

## 20. Этапы
- **Milestone 0 — Technical Spike:** загрузка Lua-мода; вызов Lua из диалога; реакция одного NPC; сохранение/загрузка; ESP ↔ JSON ↔ ESP.
- **Milestone 1 — Core Foundation:** загрузчик, логирование, конфигурация, хранилище, миграции, MCM skeleton, pipeline.
- **Milestone 2 — Social Core:** профиль, богатство, репутация, влияние, титулы, привилегии.
- **Milestone 3 — World Integration:** фракции, NPC-адаптеры, диалоги, социальные последствия.
- **Milestone 4 — Estates:** недвижимость, покупка, доступ, интерьеры и услуги.
- **Milestone 5 — Economy & Personnel:** доходы, расходы, найм и управление.
- **Milestone 6 — Politics:** организации, влияние, события и последствия.
- **Milestone 7 — World Coverage & Polish:** региональное покрытие, баланс, совместимость, документация и релиз.

## 21. Критерии подтверждения архитектуры
- Ключевые MWSE API проверены.
- Тестовый ESP вызывает Lua предсказуемо.
- Данные сохраняются и восстанавливаются.
- Миграция схемы протестирована.
- Core работает без необязательных плагинов.
- Один NPC демонстрирует контекстную социальную реакцию.
- ESP pipeline воспроизводим.
- Ограничения задокументированы.
